# disco-vm design

disco-vm runs VMs, fresh from a driver's base or from a committed VM, and
commits them to make more (ADR 26-11-03-606), on a driver that reports it
can (ADR 26-11-03-868). It runs
Windows guests on Windows (Host Compute Service), macOS and Linux guests on
macOS (Virtualization.framework; Linux from a base, ADR 26-10-31-990), Linux
guests on Linux (libkrun on KVM, ADR 26-11-03-530), and Linux guests in the
cloud on boxd or Archil from any host, or as Docker containers that
boot systemd in a user namespace of their own. There is one codebase, one binary per host OS, and one command line.
It is used two ways:

- **Standalone:** `disco-vm install | run | exec | cp | stop | commit | upgrade | rm ...`.
- **As a discobox sandbox provider:** discobox embeds `pkg/engine` as a
  library, and serves a driver it holds to a pool agent, which opens an
  engine on the served driver's client
  ([pkg/machine/served](pkg/machine/served/DESIGN.md)).

## The stack

```
  disco-vm CLI (internal/cli)           discobox provider (embeds the engine)
                 \                         /
                  pkg/engine  ── VMs, lifecycle, install, commit; no state
  ─────────── machine.Driver seam: the provider's VMs, committed or not; Machine is machine.Guest ───────────
           machine/local (store + shim on this host's disk)              machine/docker (any)   machine/boxd (any)   machine/archil (any)
   machine/hcs (windows)  machine/vz (darwin)  machine/libkrun (linux)  machine/fake    │                     │                      │
          │                     │                     │                    │           │                     │                      │
 HCS VM (vmcompute)    VZ VM (its shim's)    krun-launch (its shim's)  host process  container + userns    boxd microVM       Firecracker sandbox
          │                     │                     │                    │         (Engine API)         (gRPC API)           (REST API)
      hvsocket                vsock                 vsock                 tcp        exec + `pipe`        Exec: sudo, tar,    process API: tar,
          └──────── port 7300 ──┴─────────────────────┴────────────────────┴──────────────┘              systemctl; no       runuser; no
            disco-vm guest (the agent), reached with pkg/guest's client                                   agent at all        agent at all
```

Everything above the seam is OS-neutral and is tested on every OS through the
fake driver, and keeps no state ([below](#the-engine-keeps-no-state-and-a-driver-keeps-it-in-its-provider)).
Above the seam a running guest is only `machine.Guest`: exec, copy in and
out, info, and an orderly shutdown (ADR 0001). How a driver provides them is
its own: the agent over a private channel, or boxd's API. Everything below it
is one package per hypervisor, selected by build tags, so each binary
contains only the drivers its OS can run (`pkg/machine/drivers`). hcs, vz, and
fake keep their state on this host's disk, through `pkg/machine/local`, which
they share. boxd's and Archil's hypervisors are in the cloud, behind an API, and a Docker
daemon may be on another host or in Docker Desktop's VM, so every binary
contains both.

## Where the design lives

Each package's `DESIGN.md` holds the decisions it owns:

- [pkg/machine](pkg/machine/DESIGN.md): the driver contract and capabilities,
  ports, windows, and cold clones. Its drivers:
  [archil](pkg/machine/archil/DESIGN.md), [boxd](pkg/machine/boxd/DESIGN.md) and [docker](pkg/machine/docker/DESIGN.md),
  and [local](pkg/machine/local/DESIGN.md), the store and shim of hcs, vz,
  and fake; and [served](pkg/machine/served/DESIGN.md), a driver an
  embedder serves over a stream under its allow-list and version, and the
  driver that is its client.
- [pkg/guest](pkg/guest/DESIGN.md): the agent protocol, HTTP between host and
  agent.
- [pkg/engine](pkg/engine/DESIGN.md): who holds a running VM, the service URL,
  VMs and how they are made, pools, and why disco-vm does not converge
  guests.

## One binary, three roles

`disco-vm` is the CLI. It is also the guest agent (`disco-vm guest`) and each
VM's supervisor (`disco-vm shim <id>`). The agent is the same program built for
the guest's GOOS. On a Windows host the guest is Windows, and on a macOS host
the guest is macOS, so the running binary is also the agent, and install bakes
in `os.Executable()`. A Docker guest is Linux, so from another host the
driver's `agent` field (`$DISCO_VM_AGENT`) names a disco-vm built for it, and
so does a Linux guest on vz, which every boot hands that agent in its initrd and refuses if it speaks
another `guest.Protocol`; `go tool task build` builds it beside the darwin
binary. On a Linux host the binary is static, so a libkrun guest's agent is
the running binary, handed it the same way. Protocol changes therefore
ship to both ends at once.

An embedder that links the engine and boots Linux guests ships no disco-vm
binary of its own: disco-vm publishes its linux agent for each module
version (discobox ADR 26-11-11-963 §10). Each commit a push to main brings,
and each `v*` tag, is pushed once as
`ghcr.io/discobox-ai/disco-vm-agent:<module version>` (the tag, or the
pseudo-version Go derives for the commit, `scripts/module-version.sh`): an
index of a scratch image per platform, linux/amd64 and linux/arm64, holding
only `/disco-vm` built from that commit with that version
(`pkg/guest/agentimage`, `go tool task release:linux-agent`). A version
already published is not pushed again, so its tag's digest never moves. The
release pulls each back by its digest with no credentials, as an embedder
does, and checks it before it prints that digest. The embedder pins the
digest beside the module version it requires, and `linuximage.PullAgent`
pulls an agent by digest alone into an owner-only cache, once, refusing one
that is not a linux executable for the guest's architecture.

A driver that reaches its guest without the agent (boxd, archil) does not
list `Capabilities.Agent`, and puts nothing of disco-vm's in the guest.

## The engine keeps no state, and a driver keeps it in its provider

disco-vm's core keeps nothing: no database, no root, and no files (ADR
26-10-23-417). `engine.Open(driver, pool)` is the whole of an engine, and
every VM is read from the driver, which reads it from its provider every
time, so any process with the provider's credentials sees
the same ones, on any host. The driver keeps what it knows on the provider's
own resources, in the provider's way:

- **docker:** labels, set when a container is made or a VM committed
  (`ai.discobox.vm.*`: pool, name, the VM it was created from, size), and
  names: a VM's container `dvm-<pool>--<name>`, a committed VM's Docker
  image `disco-vm-vm:<pool>--<name>`. Nothing is kept on the host.
- **boxd:** names, since boxd keeps no labels: a VM's machine, or a
  committed VM's snapshot, `dvm-<pool>--<name>`, at most 63 characters,
  so a pool and a name are 57 together; and what the API reports: a
  snapshot's creation, a machine's size, image, and creation. boxd does not
  say which snapshot a machine was restored from, so a boxd VM has no
  `From`; a restored machine outlives its snapshot (by hand, 2026-10-23).
  Nothing is kept on the host.
- **archil:** names, since a sandbox has no labels: a VM's sandbox,
  committed or not, `dvm-<pool>--<name>`, which Archil keeps unique, and
  its data disk `dvm-<pool>--<name>--data`, so a pool and a name are 57
  together (a sandbox's name is at most 63); and what the API reports: a sandbox's size and creation, its
  fence. Archil does not say which sandbox a fork came from, so an archil VM
  has no `From` once listed (ADR 26-11-03-676). A data disk with no
  sandbox is a VM an upgrade stopped between deleting its sandbox and making
  it again, listed with no size and the fence `none`. Nothing is kept on the
  host.
- **hcs, vz, libkrun, fake:** this host's disk is the provider, kept by
  [pkg/machine/local](pkg/machine/local/DESIGN.md) in a directory of its own.

A VM's name is unique in its pool, committed or not, the way its provider
makes names unique (a container's and a committed image's, a machine's and a
snapshot's, a claim file), and is 1 to 63 lowercase letters, digits, and
single hyphens (`machine.ValidateName`). That a VM is committed is the
caller's to record: not every provider can tell (Archil keeps a committed
sandbox as a stopped one).

**Nothing from before is read** (ADR 26-10-23-417): disco-vm is pre-alpha,
so a root's `disco-vm.db` and the layers and instances it described, the
images and tags of before ADR 26-11-03-606, and what a driver made under its
old names, are not taken in. Remove them, or
keep using the disco-vm that made them.

## A driver is given its key

A driver calls its provider with the key its `machine.Config.Keys` source
answers, asked on every call, and never reads the environment for one; the
command line's source does (`machine.KeyFromEnv`), and only the command
line's. A driver issues keys for another host to run the pool's machines
(`IssueKey`, `IssuedKeys`, `RevokeKey`; `disco-vm key issue | ls | revoke`)
that expire and cannot issue keys, or issues none (ADR 26-10-24-562;
[pkg/machine](pkg/machine/DESIGN.md#a-driver-is-given-its-key-and-issues-keys-that-cannot-issue)).
Its definition declares the key as a secret, the variables it is read from,
and every host, method, path, and header or body field it is sent in, so an
embedder can hand the driver a stand-in and swap the real key in on the way
out (`machine.SecretSends`; ADR 26-11-12-461). A secret is written and never
read back. An embedder dials every connection a driver makes to its
service, a registry it pulls a base or runtime from, or the host vz downloads
macOS media from (`machine.Config.Dial`), at the service's own address, with
no proxy variable read.

## A driver's configuration is its own

Each driver takes a configuration no other driver shares
(`machine.Config.DriverConfig`, a JSON object; ADR 26-11-11-215): docker's
daemon, archil's region, libkrun's runtime. It declares every field in its
`machine.Definition`, the shape of discobox's `sandbox.ProviderDefinition`
plus a default, a variable, and whether it is privileged, and checks it with
its own `Validator`; `machine.New` refuses a field it does not declare, and a
value it does not take, before it constructs anything, and no error quotes a
value ([pkg/machine](pkg/machine/DESIGN.md#a-drivers-configuration-is-its-own)).
`machine.Config` keeps only what the seam reads: the pool, the base, the
directory, the shim, and the key.

A driver never reads the environment for its configuration. The command line
builds it (`internal/cli/driverconfig.go`) in one of two ways that do not
mix: `--driver-config JSON|@FILE`, whole (a file of at most 1 MiB), with no
variable read and any that disagrees named in a warning; or a flag per field,
`--DRIVER-FIELD` (`--docker-host`), over the field's environment variable
(`DOCKER_HOST`). Another driver's flag is refused. The base stays
`$DISCO_VM_BASE` either way. `--help=DRIVER` lists a driver's base and fields,
as `discobox admin provider create --help=PROVIDER` does, `disco-vm drivers`
describes each driver, and `info` prints the configuration in effect. A
local driver writes the configuration to a VM's directory, owner-only, when
it starts it, and its shim reads it from there, never from its command line
or its environment.

`--debug` (`machine.SetDebug`) has a driver report every call it makes to a
service outside the process, boxd's API or the Docker daemon, and how long the
answer took.

hardware and `internal/e2e` passes with `DISCO_VM_DRIVER` set to it. See
[docs/drivers/hcs.md](docs/drivers/hcs.md), [docs/drivers/vz.md](docs/drivers/vz.md),
[docs/drivers/libkrun.md](docs/drivers/libkrun.md),

[docs/drivers/docker.md](docs/drivers/docker.md), and
[docs/drivers/archil.md](docs/drivers/archil.md). boxd's "fake API" column is
`TestConformanceFakeAPI`: the whole suite against an in-process fake of boxd's
API, which proves the driver's calls and the Exec relay but not boxd's
behavior.
